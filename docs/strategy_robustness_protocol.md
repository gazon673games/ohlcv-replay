# Протокол проверки устойчивости стратегии

Бэктесты выполняет штатный `run_workbench_backtest(WorkbenchRunRequest)`:
SDK → ограниченная доступная история → заявки → исполнения → портфельный ledger.
Исследовательская команда задаёт варианты и анализирует сохранённые результаты.
Она не содержит торговых сигналов и не рассчитывает альтернативный баланс.

Для крипто комиссия определяется maker/taker тарифом спецификации инструмента:
изменение одного общего `commission_bps` не подменяет этот тариф. Комиссионный
стресс задавать отдельной явно сохранённой спецификацией и approved catalog input;
спред и проскальзывание — настройками исполнения. Проверять фактические расходы.

Все 59 валидных проверок CY от 08.10.2026 выполнялись этим же бэктестером.
Разовые скрипты в `.scratch/cy-core-robustness/` управляли серией и отчётом.
Исходная серия сохранена в `data/cy-core-robustness-20261008/`.
Результат `core_baseline` исключён: обнаружена плата за роллирование на обычных
барах. После исправления учёта серия выполнена заново; валидный базовый прогон —
`core_baseline_fixed`. Исключение записано в исходном `experiment_plan.json`.

## Общий порядок

До запуска зафиксировать гипотезу, ядро стратегии, варианты, границу обучения,
ограничения исполнения и критерии приемлемости. Доходность лучшего исторического
варианта сама по себе не является критерием устойчивости.

| Проверка | Как задать для другой стратегии | Что оценивать |
|---|---|---|
| Базовый прогон | Один `baseline`, фиксированные капитал, валюта, правила | NAV, издержки, просадка, сделки, остаточная позиция |
| Соседние параметры | Небольшая сетка `grids`, группа `neighbors` | Минимум/медиана/максимум, доля прибыльных, провалы рядом с базой |
| Дальние значения | Именованные `cases` за пределами локальной сетки | Где исчезает эффект; не смешивать с локальной семьёй |
| Фаза входа | Варианты времени около входа и далеко от него | Насколько эффект привязан к конкретной минуте/сессии |
| Масштаб свечей | `params` времени/окон, при необходимости другой approved dataset | Сохранение временной длины индикаторов, изменение исполнения |
| Отключение правил | Без фильтров, календарных запретов, отдельно long/short | Вклад каждого правила; реальные отключения задаёт сама стратегия |
| Управление капиталом | Без добора/плеча, затем с ними | Отдельно эффект сигнала и риск масштабирования |
| Издержки | `request_overrides`: комиссии, спред, проскальзывание, ролл | Полные повторные бэктесты с новым исполнением и размером позиции |
| Периоды/режимы | Фиксированный `split_date`, годовые таблицы | Обучение и последующая хронологическая проверка, плохие годы |
| Новый старт | `from_date` в отдельном case | Результат с исходным капиталом, без накопленной позиции |
| Отбор → новый старт | `fresh_selected_group` | Лучший по доходности **до** split, отдельный прогон после split |
| Зависимость от немногих сделок | Автоматический анализ `trades.parquet` | Cash PF, доля лучших 5/10, диагностическое вычитание их PnL |
| Перестановки блоков дней | `bootstrap_blocks_days`, iterations, seed | Чувствительность к порядку зависимых доходностей |
| Множественный перебор | Явные `family_groups` | PBO, reality check, deflated Sharpe по семейству кандидатов |
| Бухгалтерия/качество | Автоматический аудит каждого native run | Ledger=NAV исполнения, накопленные cash flows, gates, ролл |

Дополнительно при наличии данных заранее планировать проверку на другом
инструменте, walk-forward с несколькими границами, альтернативном правиле ролла,
задержке и ограничениях ликвидности. Они задаются отдельными cases/сериями;
команда не придумывает недостающие данные и не выбирает торговые правила сама.

## Общая очередь Workbench

Подготовка, запуск и просмотр исследования доступны через [MCP и CLI](mcp_research.md).
Команда `backtest robustness-prepare --config <protocol.json>` фиксирует план,
`robustness-submit <experiment_id>` ставит его в общую очередь приложения,
`robustness-status <experiment_id>` читает статус и компактную таблицу. Источники
SDK фиксируются до постановки в очередь; изменение runtime или входов требует
нового плана. Данные и результаты старых исследований сохраняют исходную идентичность.

## Повторяемая команда

Из `backtest_engine/`:

```powershell
uv run python tools/run_robustness_protocol.py tools/robustness_example.json --plan-only
uv run python tools/run_robustness_protocol.py tools/robustness_example.json --resume
```

Пример содержит 24 обычных варианта и дополнительный выбранный новый старт.
Он использует уже сохранённый CY request; для другой стратегии скопировать
пример в `data/<experiment>/protocol.json`, указать свой `base_request`, параметры,
approved dataset, капитал/валюту, даты и новый `output_root`.
`base_request` — JSON обычного `WorkbenchRunRequest`, как в сохранённом запуске:

```json
{
  "script_source": "SDK_CATALOG_STRATEGY = \"my_strategy\"\n",
  "script_language": "python",
  "dataset_path": "dataset/bars.parquet",
  "quality_approval_path": "dataset/approval.json",
  "catalog_path": "catalog.json",
  "dataset_id": "approved-dataset-id",
  "catalog_enforcement": "strict",
  "initial_capital": 1000,
  "base_currency": "USDT",
  "from_date": "2024-01-01",
  "params": {}
}
```

Спецификации инструмента, календарь, исполнение и издержки необходимо явно
добавить в этот request в соответствии с рынком. Пример формы выше не является
готовым набором рыночных допущений. Для SDK использовать каталог/его draft либо
уже замороженный snapshot; разрешение зависимостей выполняет штатный SDK.
Не расширять допустимые параметры стратегии автоматически: исследовательский
draft со сменой bounds задаётся явно и сохраняется отдельно от общего каталога.

Пути протокола разрешаются относительно его JSON. Пути исходного request и
`request_overrides` — относительно JSON исходного request.
`cases[].params` меняет параметры стратегии, `request_overrides` — настройки
бэктестера. Опечатки в полях request и протокола отвергаются. Сетка не должна
превышать `max_runs` (до 500); workers от 1 до 4. Все sources и параметры
проверяются до начала исполнения. Полный quality gate выполняет бэктестер.

Каждая серия содержит:

- `manifest.json`: план, замороженные запросы/SDK helpers, SHA256 данных,
  approvals, спецификаций, календаря, catalog, valuation rates и runtime sources;
- `runtime_sources.zip`: снимок Python исходников backend и установленного SDK;
- `runs/`: штатные артефакты новых бэктестов; `checkpoints/`: состояние каждого;
- `summary`, `annual`, `families`, `reconciliation`, `block_bootstrap`,
  `selection_bias`, `deflated_sharpe` в CSV/JSON/Parquet;
- `daily/`: дневная NAV и доходности из ledger; `report.html`, `result.json`;
- `training_selection.json`, если задан `fresh_selected_group`.

`--resume` допускает только совпадающий план, входы, runtime и хеши результатов.
Изменение стратегии, данных, пакетов, seed или настроек требует нового output root.
Предыдущая ошибка остаётся видимой и требует новой серии; чужой готовый run
никогда не перезаписывается. `status=completed` означает техническое завершение,
а `robustness_verdict=requires_review` оставляет исследовательское решение человеку.

## Анализ уже выполненных бэктестов

Задать `cases[].existing_run` для каждого native каталога; `base_request` не нужен.
В этом режиме параметры и капитал читаются из фактического `config.json` старого
прогона. Это повторный аудит и анализ, а не новое исполнение и не доказательство
того, что старые результаты получены текущей версией программы.

```powershell
uv run python tools/run_robustness_protocol.py ../data/cy-core-robustness-20261008/protocol.json --analyze-existing
```

Все 59 CY cases внесены в этот общий протокол, исходный результат не изменяется.
Новый отчёт: `data/cy-core-robustness-20261008/protocol-report/report.html`.

## Статистические оговорки

Доходности рассчитываются по валюте портфеля из фактической ledger NAV.
Просадка считается на каждой свечной оценке, годовые и train/check доходности
относятся ко времени **оценки**, а не к более раннему времени сигнала.
Native ledger записывает aware timestamps как UTC-naive; аудит сравнивает
сериализованные моменты с event valuation в микросекундах, не изменяя файлы.
Разбиение дней использует записанные часы ledger (для крипто — UTC).
Новый старт после split не наследует капитал и позицию обучающего прогона;
предыдущие бары остаются доступны как причинный прогрев индикатора.

Общий bootstrap использует уже существующую реализацию backend: нециклические
блоки последовательных торговых дней, эмпирические квантили 5/50/95%. В первой
разовой CY аналитике использовались циклические блоки и 2.5/97.5%; поэтому её
интервалы отличаются. Seed фиксируется. Менее двух блоков дней — явный skip.
Доля убыточных перестановок не является вероятностью будущего убытка.

Reality check использует IID перестановки дневных доходностей и не устраняет
всю временную зависимость. PBO и deflated Sharpe — диагностические методы.
Неполное семейство или несовпадающие дневные даты дают skip, а не удаление
неудобных кандидатов. Не торгующие варианты остаются в статистике семейства;
отбор на обучении требует реальных исполнений в обучающем периоде.

Вычитание PnL лучших сделок — диагностическая атрибуция без нового сложного
процента; cash PF сделок отличается от показателя на процентных доходностях.
Остаточная позиция оценивается согласно native end-of-data policy.
История CY уже изучалась: разделение 2025-01-01 не делает её невиданным holdout.
Константное ГО, ролл `exclude_gap`, свечное исполнение без исторического стакана
и один инструмент ограничивают выводы первой серии; эти допущения сохраняются
в протоколе, а не исчезают из-за положительных результатов.
